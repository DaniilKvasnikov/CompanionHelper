# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Working style (read first)

**Do only what was asked. Don't add unrequested features, variants, or "nice to have" extras.** If something beyond the request seems useful (extra buttons, presets, options, refactors), *ask first* whether it's wanted rather than building it. Scope creep — however well-intentioned — is not welcome here; a smaller change that does exactly what was asked is always preferred.

## What this is

A modular menu system for a Stream Deck driven through [Bitfocus Companion](https://bitfocus.io/companion). The on-disk `menus/` folder tree defines a hierarchy of submenus and script-backed buttons; this FastAPI service renders that hierarchy onto the deck and runs the scripts when buttons are pressed.

## Commands

```bash
pip install -r requirements.txt   # fastapi, uvicorn
python main.py                    # serves on 0.0.0.0:7878

pip install -r requirements-dev.txt   # adds pytest
python -m pytest                       # run tests (tests/, ~0.3s, no live Companion/PDQ)
python -m pytest tests/test_pdq.py -q  # a single file
```

- `POST /press?page=&row=&col=` — called by every deck button on press (Companion → here, HTTP).
- `POST /reload` — rebuild the menu tree from disk and redraw active pages (use after editing `menus/`).
- `POST /touch/buttons` / `POST /touch/ping` — a TouchDesigner client sets its deck buttons / keeps them alive. See "Touch" below.
- `GET /` — the read-only **web status page** (markup in `web/index.html`); `GET /status` — its JSON snapshot; `GET /logs` — the **log window** (web/logs.html) that says why a value is not being read, `GET /logs.json` — the data it renders. See "Web status page" below.

**Several decks.** One server can drive more than one Stream Deck: each deck's buttons POST their own `page`, and all menu state is kept **per page** ([core/state.py](core/state.py)), so two decks sit on different menus at the same time. `DECK_PAGES` ([core/config.py](core/config.py), one page per deck) lists the pages drawn at startup, so a second deck is not blank until its first press.

Two transports, opposite directions: **presses come in over HTTP** (FastAPI), **button visuals go out over OSC/UDP** to Companion's OSC listener (`OSC_HOST`/`OSC_PORT` 12321 in [core/config.py](core/config.py)). Companion must have OSC control enabled.

## Machine-local configuration (config.local.json)

The repo is pulled on several machines with different local values (deck page, PDQ/FFS paths, OSC endpoints, sync jobs). **Never edit those into `core/config.py`** — a pull on another machine would conflict. The split:

- `core/config.py` holds **shared defaults only**. Per-machine values go in a git-ignored **`config.local.json`** next to the project root (template: `config.local.example.json`, tracked). At import, the bottom block of `config.py` reads it and **replaces** each named constant (whole value, by name). Read it once — a knob changed in the JSON needs a server restart to take effect, same as editing `config.py`.
- Absent keys keep the code default (so future default changes still arrive on pull); keys starting with `_` are ignored (notes); an **unknown key is logged as a warning and skipped** — a typo must not silently break a knob. Missing/invalid file → defaults + a warning, never a crash.
- Only names that are uppercase data constants can be overridden (a JSON `"Kind"` etc. is ignored). Values are JSON: replace tuples/lists/dicts wholly (`FFS_JOBS` is an array of `[label, path]` pairs). Use forward slashes in Windows paths.
- Machine-local **data** follows the same pattern: `pc_aliases.txt` is git-ignored (template `pc_aliases.example.txt`); `deploy/start-companionhelper.bat` auto-uses `project\.venv` so it never needs a per-machine edit. Both files are named in `.gitignore`.
- New per-machine knobs: keep the default in `config.py`, mention the key in `config.local.example.json`.

## Key architectural constraint

Companion's remote API can only change a button's **visuals** (text, colors), never its **action**. So dynamic submenus are impossible to build on Companion's side. Instead:

**Dumb deck, smart server.** Every button on a controlled page is configured in Companion to send the *same* generic `POST /press` with its own `page/row/col`. This server owns all state and logic, resolves what that coordinate means in the current menu, acts, and then re-pushes styles to **all 32 cells** of that page to reflect the new view. State is kept per page, so several decks (see `DECK_PAGES`) work side by side without touching each other.

## Data flow (one press)

1. Deck button → `POST /press?page&row&col` ([main.py](main.py)).
2. [core/dispatcher.py](core/dispatcher.py) `handle_press` resolves current menu ([core/loader.py](core/loader.py) `resolve` walking [core/state.py](core/state.py) `path`), maps the cell via [core/layout.py](core/layout.py) `build_layout`, and acts:
   - **submenu** → push folder onto `state.path`, redraw;
   - **back / prev / next** → adjust nav state, redraw;
   - **command / feedback** → run the script ([core/runner.py](core/runner.py)) and write its result onto that one button.
3. Redraw = [core/render.py](core/render.py) `draw` via [core/companion.py](core/companion.py).

## Rendering performance

A naive redraw would be dozens of HTTP round-trips and is visibly slow. Two things keep it fast, in [core/render.py](core/render.py) / [core/companion.py](core/companion.py) / [core/osc.py](core/osc.py):

- **OSC/UDP for everything** — text (`/location/<p>/<r>/<c>/style/text <text>`) and colors (`/style/bgcolor` and `/style/color` as `r g b` 0-255) are sent fire-and-forget, no round-trip. A text-only change is one message; a color change is three (`companion.set_style`). Colors are stored as `#rrggbb` and converted to r/g/b in `companion._rgb`.
- **Diffing** — `PageState.rendered` caches each cell's last `(text, bg, fg)`; `render._emit` pushes only cells whose style changed, and prefers `set_text` (1 msg) over `set_style` (3 msgs) when only text differs. A feedback poll touches ~1–2 cells, not 32. Single-button updates go through `render.update_cell` so the cache stays consistent.

[core/osc.py](core/osc.py) writes OSC 1.0 messages by hand (no dependency). Knobs live in [core/config.py](core/config.py) (`OSC_HOST`/`OSC_PORT`). If you bypass `render`/`companion` to talk to Companion directly, update `PageState.rendered` too or the diff will skip real changes.

## Menu tree conventions (`menus/`)

The filesystem *is* the menu hierarchy. Naming (see [core/model.py](core/model.py) `make_label`):

- `NN_` prefix → ordering only; stripped from the display label.
- `01_lights/` (folder) → **submenu**.
- `01_on.py` (file) → **command button**; its first stdout line shows on press.
- `01_cpu.fb.py` (`.fb` before the extension) → **feedback button**; polled every `FEEDBACK_INTERVAL`s and on menu entry, stdout → button text.
- `01_install.pdq` → **PDQ Deploy button**; a JSON config, not an executable (see below).

Scripts run by extension ([core/runner.py](core/runner.py) `RUNNERS`): `.py .sh .ps1 .bat .cmd`, else executed directly. `cwd` is the script's own folder. `run_script` special-cases `.pdq` before the generic path.

## PDQ Deploy integration

Split across two channels ([core/pdq.py](core/pdq.py)), because PDQ Deploy 20.x separates them:

- **Reads** (package / target-list names, and the **deployment journal**) come from PDQ's **SQLite database** (`PDQ_DB_PATH`) — the CLI has no command to enumerate packages or target lists, and on-prem PDQ Deploy has **no REST API** (only the cloud PDQ Connect does; the console and every community tool read the DB). `_connect` copies `Database.db` + `-wal` + `-shm` to a temp dir and reads the copy: reading the live WAL DB read-only silently misses data still in the `-wal` (Windows read-only-WAL limitation), and the copy also avoids locking the running DB.
- **Deploys** go through `PDQDeploy.exe` (`PDQ_DEPLOY_EXE`).

**The journal.** `pdq.recent_deployments(limit)` reads `Deployments` (`DeploymentId`, `PackageName`, `Status` — `Running`/`Success`/`Failed`/…) newest first, and with `with_targets` attaches the `DeploymentComputers` rows of each one (where it went, how each machine ended) — one snapshot copy serves the whole call. The schema is **undocumented and varies between builds**, so every column of the row is kept for the caller to pick from (webstatus does that with case-insensitive `_pick`), ordering falls back to `rowid` when `DeploymentId` is absent, and a table/column that is missing raises `PdqSchemaError` **listing the tables/columns that DO exist** — that message goes to the log window, so "почему пусто" is answerable. `python -m core.pdq deployments [N]` prints the same thing from a console.

A `.pdq` button is a JSON config (`note` keys ignored), resolved by `args_from_config`:

- `{"package":"Install","targets":["PC1","PC2"]}` → `Deploy -Package -Targets` (specific PCs).
- `{"package":"Install","target_list":"All"}` → members read from the DB and **expanded into `-Targets`**. This is how we hit a Target List — the CLI has no `-TargetList` option, so we don't rely on Schedules.
- `{"schedule":12}` → `StartSchedule 12` (only if you keep Schedules in PDQ).

`runner.run_script` routes `.pdq` to `pdq.run_config` (uses `PDQ_TIMEOUT`); the deployment output shows on the button. Discovery: `python -m core.pdq packages | lists | members "<list>" | deployments [N]`.

**Requirements**: Enterprise license, PDQ installed on **this** machine (CLI is local-only), background service running, and `main.py` started **elevated (as admin)** or `Deploy` fails with permission denied. Note the install path is `Program Files (x86)`.

## Dynamic menus (providers) and the PC browser

Menus can be generated at runtime, not just from folders. Two node types in [core/model.py](core/model.py) beyond the file-backed `CommandNode`:

- **`MenuNode.provider`** — a callable `provider(node) -> [child nodes]`. `children_of(node)` returns the provider's output if set, else static `children`. `loader.resolve` and `layout.build_layout` both go through `children_of`, so dynamic branches materialize lazily as you navigate. `context` carries data down a branch (e.g. which PC); `color_fn` gives a button a runtime color.
- **`ActionNode`** — a button that runs a Python callable (`on_press`) instead of a file. `after` decides what follows: `'text'` (show the returned string on the button), `'rerender'`, or `'back'` (pop up a level, e.g. after picking from a list).

In the dispatcher, `MenuNode` presses drill in; everything else routes by node type — `ActionNode` → `_run_action`, `CommandNode` → `_run_command`. `Slot.color` (from a node's `color_fn`) overrides the kind color in `render`.

Two dynamic features so far, both built on the same PDQ catalog:

[core/pcbrowser.py](core/pcbrowser.py) — a "ПК" button on the main menu (`attach` inserts it). Inside: a "change list" picker submenu (the shared `list_picker`), then one button per host in the **active PDQ target list** (default: first list), each colored by ping. Selecting a host opens a package menu; pressing a package deploys it to **that single host**. This module **owns the catalog + selection state** (active list, lists, packages, members, ping, aliases), cached so providers never hit the DB per render; refresh on start/reload. An optional **aliases file** (`PC_ALIASES_FILE`, lines `ip = alias`) is loaded in `refresh_catalog`; `host_label(host)` shows the alias above the ip and `members()` sorts by `_host_sort_key` (aliased hosts first, by alias, then the rest by host). Both the "ПК" menu and pdqmenu's "Выбор ПК" render hosts through `host_label`. A background ping sweep ([core/pcbrowser.py](core/pcbrowser.py) `start`, every `PING_INTERVAL`) updates status and calls `dispatcher.render_all_pages` — the render diff means only recolored buttons are pushed. `_ping_host` requires an actual reply (`TTL=` in output), since Windows `ping` returns 0 even when unreachable.

[core/pdqmenu.py](core/pdqmenu.py) — a "PDQ" button (inserted right after "ПК") for **batch** deploys to the active list. Inside: **Лист** (reuses `pcbrowser.list_picker`), **Выбор ПК** (toggle each host in/out with `on_press` → `toggle_host`, `after='rerender'`; ✓/✗ marker, ping color, dim `PC_OFF` when off), **Область** (an `ActionNode` toggling `_scope_active` between the whole list and enabled-only), then one button per package that deploys to `targets()` in a single `pdq.run`. It reads the catalog from `pcbrowser` and owns only the per-list `_disabled` set (absent host ⇒ enabled, so all-on by default) and the scope flag; no DB access, no background thread.

[core/aoto.py](core/aoto.py) — an "AOTO" button (after ПК/PDQ) for HTTP control of Aoto LED processors, grouped. **Groups are files** in `aoto/groups/*.txt` (one controller `host:port` per line, `#` comments, `NN_` filename prefix for ordering); **commands** are shared across groups in `aoto/commands.json`. AOTO → group list → per-group command menu. A command press fires an HTTP request (stdlib `urllib`) to **every** controller in the group in parallel and shows an aggregated summary (`OK n/n`, else `ERR k/n`). A command with a `response_field` is a **status** button: that dotted field (e.g. `obj.brightness`, `obj.hdrSetting`) is read from each controller's JSON reply. An optional `labels` map (`{"0":"from input","1":"SDR",…}`) turns raw values into names (`_map`). The group is aggregated by `_format_values` (all equal → the value; numbers differ → a `min-max` range; else a `/`-joined distinct list) with a `(k/n)` suffix on partial failure. The `_status` cache holds **per-controller** results `[(addr, ok, value), …]`, refreshed by a background poller (`start`, every `AOTO_POLL_INTERVAL`, calls `dispatcher.render_all_pages`) and re-polled on press. When the group **agrees**, the status button is a re-poll `ActionNode` (`after='rerender'`); when it **disagrees** (`_values_differ`), the same slot becomes a `MenuNode` that drills into `_status_detail` — one button per controller showing its IP's last octet and value (e.g. `.216 / HLG`). Status buttons/details are `Kind.COMMAND` with a green `color_fn` — deliberately **not** `Kind.FEEDBACK`, so the file-based feedback poller (which does `run_script(node.path)`) never touches these pathless nodes. Catalog + cache live here; providers only read them, HTTP happens on press or in the poller. Config/paths in [core/config.py](core/config.py) (`AOTO_*`).

**Brightness submenu.** Each AOTO group also gets a **«Управление яркостью»** submenu (`_brightness_children`), appended by `_group_commands` **only when the status command named `AOTO_BRIGHTNESS_STATUS_LABEL` (default `Яркость`) exists** — that same command both reads the current value and gates the menu. Inside: the current brightness (`_brightness_text` re-poll `ActionNode`, green; shown in **nits plus the % of the group's maximum**, e.g. `1496 (100%)`, range `600-800 (60-80%)` when controllers disagree), **Темнее / Ярче** (manual step), **Темнее 5% / Ярче 5%** (step = `AOTO_BRIGHTNESS_PERCENT` % of the group's ceiling) and **Темнее 1% / Ярче 1%** (step = `AOTO_BRIGHTNESS_PERCENT_FINE` % — the fine nudge), and step controls **Шаг ÷2 / Шаг N / Шаг ×2**. All +/- buttons are **per-controller**: `_adjust_brightness_by` reads each controller's brightness via the status command, shifts by the step, clamps to `[AOTO_BRIGHTNESS_MIN, brightness_limit(group)]`, and writes it back via `AOTO_SET_BRIGHTNESS_PATH` (body `{AOTO_SET_BRIGHTNESS_KEY: value}`), then re-polls so the shown value is truthful. A percentage button's step is `_percent_step(limit, percent)` = `max(1, round(limit * percent / 100))`, and its label is built from the config value, so the two never drift apart. The ceiling is per-group with this priority: the **`@max = <n>` directive in the group file** (`aoto/groups/*.txt`, parsed by `_parse_group_lines` — the same directive style the OSC groups use) > `AOTO_BRIGHTNESS_LIMITS[group]` > `AOTO_BRIGHTNESS_LIMIT_DEFAULT` (= 1500). The manual step is **AOTO-wide** module state (`_step`, `get_step`/`_scale_step`, floored at 1). All `Kind.COMMAND` + `After.RERENDER`; config in `AOTO_BRIGHTNESS_*`.

**Dynamic Range submenu.** Each AOTO group also gets a **«Dynamic Range»** submenu (`_hdr_children`), appended by `_group_commands` **only when the status command named `AOTO_HDR_STATUS_LABEL` (default `HDR`) exists** (gate only — like the brightness gate; the HDR reader isn't read here). Inside: one plain setter button per mode in `AOTO_HDR_MODES` (default `SDR`/`HLG`/`PQ`). Pressing one fires `run_group` with `_set_hdr_cmd(value)` — `POST AOTO_SET_HDR_PATH`, body `{AOTO_SET_HDR_KEY: value, **AOTO_SET_HDR_EXTRA}` (the varied `hdrSetting` plus the fixed `maximumBrightness`/`coefficient`) — to every controller, and shows the `OK n/n` summary (`Kind.COMMAND` + `After.TEXT`). **Note:** the `setHDR` *write* values (SDR=2/HLG=3/PQ=4) deliberately differ from the `getGlobalSettings` *read* scale in commands.json (SDR=1/HLG=2/PQ=3); this submenu only writes, so it shows no status. Config in `AOTO_HDR_*` / `AOTO_SET_HDR_*`.

**Presets browser.** Every AOTO group also gets a **«Пресеты»** submenu (appended last by `_group_commands`) that browses the on-disk tree under `AOTO_PRESETS_DIR` (`aoto/presets/`) — folders are preset groups, `*.json` files are presets (see [core/aotopresets.py](core/aotopresets.py) for the file format and the full description). A preset is a **self-contained** JSON array of parameters `{name?, set{path, key, value, method?, extra?}, get{path, field}}`; pressing it applies every `set` (`POST path`, body `{key: value, **extra}`) to **every controller of the current group** via `aoto.probe`/`aoto.fire` (aggregated `OK k/m`). **Записать пресет** captures the current group state into a new file: it reads each parameter through its `get` spec (POST `path`, field from the reply) and stores the value **only when the whole group agrees**; an optional parameter-level `map` (`{"read": write}`) converts read values to write values (e.g. the HDR read SDR=1/… vs write SDR=2/… scales). The parameters available for capture come from `parameters.json` (template `parameters.example.json`, both next to the tree) — the list grows by editing that file, never by code. **Новая папка** creates a preset folder; new presets/folders are auto-named (rename them on a PC). The module owns a cached tree + catalog, refreshed by `refresh()` on start/reload; providers read caches only, writes/HTTP happen on press. Invalid preset files are skipped with a warning.

[core/touch.py](core/touch.py) — a "Touch" tab whose **buttons come from TouchDesigner itself**. A TD client (any Python in a .toe — the shipped template is [touch/client.example.py](touch/client.example.py), the full wire reference is [TOUCH_API_GUIDE.md](TOUCH_API_GUIDE.md)) drives the tab over HTTP: **`POST /touch/buttons`** `{"client", "label"?, "host"?, "port"?, "address"?, "buttons":[{"id","label"?,"color"?,"active"?}]}` registers/refreshes it and **replaces** its whole button list, and **`POST /touch/ping`** `{"client"}` is the heartbeat that keeps it on the deck. `host`/`port`/`address` are where its presses go and default to `TOUCH_OSC_HOST`/`TOUCH_OSC_PORT`/`TOUCH_OSC_ADDRESS`; an entry needs only an `id` (label defaults to it, a bad `color` is dropped with a warning, `active: true` gives the deck's green highlight — everything else is a default kind color). Every live client becomes a **submenu** on the Touch tab (label above its id, sorted by label); the only deck-side buttons are the framework's own Back/Home and paging, exactly as the request asked ("everything except Back comes from TD"). Pressing a button fires **one** fire-and-forget OSC message to that client's `host:port/address` with the button `id` as a string argument (`press` → `osc.send_to`) — that is how the press is proxied back into TouchDesigner; there is no subscription, the client just listens on OSC. The module owns the client registry (in memory, guarded by its own lock); providers only read it, HTTP/OSC happen on request or press. A sweeper (`start`, every `TOUCH_SWEEP_INTERVAL`, started in `main.lifespan`) **drops any client silent for `TOUCH_CLIENT_TIMEOUT`** seconds and redraws the deck, so a closed .toe leaves no dead buttons; an unknown `client` in a ping is answered `{"status": "unknown"}` (a ping never registers — the client should re-post its buttons), and a payload that cannot be used is a 400. Config in [core/config.py](core/config.py) (`TOUCH_*`). The old file-based groups (`touch/groups/*.txt`, `@address`, `file`/`base`/`fps`) are **gone**.

[core/osc_buttons.py](core/osc_buttons.py) — an "OSC" tab (after ПК/PDQ/AOTO/Touch) for firing **arbitrary OSC messages**. **Groups are files** in `osc/groups/*.txt` (one `label = /address arg arg` per line, `#` comments, `NN_` filename prefix for ordering). OSC → group list → per-group buttons; pressing one sends a single fire-and-forget message and shows `OK`. The difference from `touch` is **where the address lives**: there it belongs to the group and every button sends its filename to it, here each button carries its **own address and its own arguments** — which is what driving operator parameters needs. A group retargets with `@host =` / `@port =` directive lines (parsed in `_parse_group`), falling back to `OSC_BUTTONS_HOST`/`OSC_BUTTONS_PORT`. The message is parsed by `_parse_message` with `shlex.split` (so `"две слова"` stays one argument) and each token typed by `_typed` — int if it parses as one, else float, else the string as written; a line whose first token is not a `/address` is skipped with a warning. A button with no arguments sends the address alone, which is how you fire a pulse parameter. Catalog read from disk on start/reload; **no poller and no cache** — nothing is read back. Defaults point at [oscctl](https://github.com/DaniilKvasnikov/oscctl), where the address is an operator path plus a parameter name. Config/paths in [core/config.py](core/config.py) (`OSC_BUTTONS_*`).

[core/pixelhue.py](core/pixelhue.py) — a "PixelHue" tab (after ПК/PDQ/AOTO/Touch/OSC) for HTTP control of one **PixelHue Q8** node (also P10/P20/P80). Device address/port/nodeId live in config (`PIXELHUE_*`, per-machine via `config.local.json`). **Auth is a passwordless JWT**: HS256, payload `{SN}`, secret = `startTime` from the public `node/open-detail`; `build_token` does it on stdlib (`hmac`/`hashlib`/`base64`), the token is cached in memory only and rebuilt automatically on HTTP 401 (device reboot changed `startTime`). All commands go through **`/unico/v1`** (a superset of the documented `/pixelhue/v1`, which 404s on `layers/window`/`zorder`); bodies follow the shapes from the [companion-module-pixelhue-switcher](https://github.com/bitfocus/companion-module-pixelhue-switcher) reverse-engineering (see `PIXELHUE_API_GUIDE.md`). The tab shows a status button (node version + online/offline, re-polls on press), global **«Затемнение»**/**«Стоп-кадр»** toggles (the deck's Russian words for FTB and Freeze — the wire/config names stay `ftb`/`freeze`; one array request across every usable screen, label shows вкл/выкл/частично, green when all on), a **Mapping** toggle (the PixelFlow "Device→Location→Mapping" switch: `PUT /unico/v1/node/interface-location` `{"nodeId", "enable"}`, on/off state read back from the same resource via GET `?nodeId=` — `node/detail.location` does NOT reflect the PUT, so never trust it for this flag), a per-screen submenu (**Экраны**: Take/Cut/Freeze/FTB toggles per real output; screens come from `screen/list-detail` and MVR screens — `screenIdObj.type` in `PIXELHUE_SKIP_SCREEN_TYPES` (8) — plus blank/invalid ones are dropped by `parse_screens`), and a **Пресеты** submenu from `GET /preset` (each applies to the program region). The module owns a node/screen/preset cache; a background poller (`start`, every `PIXELHUE_POLL_INTERVAL`, calls `dispatcher.render_all_pages`) keeps freeze/ftb states truthful — the render diff pushes only changed buttons. Poll failures keep the last good screen/preset list (only the node flips to offline). Providers only read caches; HTTP happens on press or in the poller. `Take` = fade `PIXELHUE_TAKE_TIME_MS`, `Cut` = instant, `FTB` fade `PIXELHUE_FTB_TIME_MS`. Config in [core/config.py](core/config.py) (`PIXELHUE_*`).

[core/ffs.py](core/ffs.py) — a "Sync" tab for running **FreeFileSync** batch jobs. Jobs are configured in [core/config.py](core/config.py) as `FFS_JOBS = [(label, path-to-.ffs_batch), …]` — one button each. Pressing runs `FFS_EXE <batch>` (`subprocess.run`, `FFS_TIMEOUT`) and shows `OK` (exit 0) or `ERR …` (non-zero exit / missing exe / timeout) on the button. **Stateless** — reads `FFS_JOBS` from config, so no disk catalog, no poller, nothing to refresh; the subprocess runs outside `state.lock` (dispatcher runs `on_press` after releasing it). Fail-soft at the exe edge (`# noqa: BLE001`).

[core/develop.py](core/develop.py) — a "Develop" tab (appended last on the main menu) with **Pull & Restart** and **Открыть статус**. *Pull & Restart* runs `git pull` in `PROJECT_ROOT` and, on success, restarts the process via `os.execv(sys.executable, [sys.executable, *sys.argv])` so new code takes effect. The pull result (`Pulled` / `Up to date`, or `ERR …`) is shown on the button first; the restart is scheduled `RESTART_DELAY` seconds later (a `threading.Timer` in `_schedule_restart`) so the deck renders that text before the process is replaced. A failed pull shows `ERR` and does **not** restart. *Открыть статус* opens the **web status page** (see below) in this machine's default browser via `webbrowser.open(webstatus.page_url())` — the page URL is built by `webstatus` (the module that owns the page), and a missing browser becomes `ERR` text rather than a crash. Fail-soft at both the git and the browser edge (`# noqa: BLE001`); no catalog, no poller, nothing to refresh. Config in [core/config.py](core/config.py) (`PROJECT_ROOT`, `GIT_PULL_TIMEOUT`, `RESTART_DELAY`; the URL follows `PORT`).

**Active-state coloring.** An action command may declare `active_status` (the label of a status command) + `active_value`; its button then goes green (`_active_color`) when the group's agreed value for that status equals `active_value` — e.g. the Вход/Блэкаут/Фриз buttons highlight whichever screen type is currently active. Such buttons press via `_apply_tracked` (apply, then re-poll the referenced status so the highlight is truthful) with `after='rerender'`. A status command marked `"hidden": true` is polled for state but **not rendered** as a button — the way to track a value only for coloring, without adding a visible status button.

## Grid & layout

Fixed 8×4 (Stream Deck XL). Content fills rows 0–2 in reading order (24 slots/page); the bottom row (`NAV_ROW`) is reserved for **Back** and **Home** (bottom-left, cols 0/1) and **Prev/Next** paging (bottom-right), shown only when applicable. Back and Home appear together whenever `depth > 0`: **Back** pops one level (`Kind.BACK`), **Home** clears the path to the root menu (`Kind.HOME`, dispatched like an "enter" so root feedback refreshes). Change `GRID_ROWS`/`GRID_COLS`/`NAV_ROW` in [core/config.py](core/config.py) for other deck sizes.

## State & concurrency

Per-Companion-page state lives in [core/state.py](core/state.py) (`path`, `page_index`, cached `feedback_values`), guarded by a single `RLock` shared between the FastAPI request thread and the background feedback poller ([core/feedback.py](core/feedback.py), a daemon thread started in `main.lifespan`). OSC sends fail soft — a socket error is logged and rendering continues.

## Progress countdown (custom variable)

[core/progress.py](core/progress.py) keeps a Companion **custom variable** `$(custom:Progress)` updated with a **0..100** progress value toward the next feedback refresh (0 right after a refresh, filling to 100 as the next approaches — a progress-bar percentage, `percent()`), so a button on an auto-updating page can show a bar. A daemon thread (`start`, started in `main.lifespan`) publishes once per `PROGRESS_TICK` via `companion.set_custom_variable`; the feedback poller's `on_cycle=progress.mark` resets `_next_due` at the end of each cycle so the value stays synced to the real cadence instead of free-running. Custom variables are **global** (not per-page), so the value is the same everywhere — the "only on auto-updating pages" part is just where you place `$(custom:Progress)`. This is the one Companion write that legitimately bypasses the `render` cell diff (it's not a button), so it goes straight through `companion`/`osc`. Names/tick live in [core/config.py](core/config.py) (`PROGRESS_VAR`, `PROGRESS_TICK`).

## Web status page

`GET /` serves a **read-only** page (markup in `web/index.html`, re-read on every request so it can be edited without restarting the server) showing the live state of everything the deck can turn; `GET /status` serves the same data as JSON for that page. It is a monitor: nothing on it writes to a device or to the deck. [core/webstatus.py](core/webstatus.py) collects the data; [main.py](main.py) only wires the routes and `webstatus.start()` in the lifespan. The **Develop** tab has an **Открыть статус** button that opens the page in the server machine's browser (`develop.open_status_page` → `webstatus.page_url()`).

**One screen, no scrolling.** The page is meant to be *watched*, so it must not need scrolling: `body` is `height: 100vh; overflow: hidden`, the four panels sit in a **2×2 grid** (ПК | AOTO on top, PDQ | PixelHue below; the right column is a little wider because AOTO/PixelHue carry values), the font size is driven by a single `--fs` variable, and after every render `fit()` shrinks `--fs` (down to 8.5px) until nothing overflows. Only if that is still not enough does a panel get its own scrollbar — the page itself never scrolls. Details that would add rows (per-controller values, ping age, a deployment's targets and raw columns, what FTB means) live in native `title` tooltips. Measured in a real browser at 1904×985 (panels 818×465 and 1063×465), 1584×805 and 1350×673 with the live Aoto controller, a journal and two screens: `pageScrolls false`, every panel overflow 0, font stayed at 15px.

**The log window (`GET /logs`, `web/logs.html`).** A monitor that says "ERR" is useless: it has to say *why*. The page's **Логи** button opens `/logs` in a separate window (scrolling allowed there) which renders `GET /logs.json`, i.e. the open problems from [core/diag.py](core/diag.py) — one row per problem with a repeat counter, the first/last time seen, the source, **the exact thing that was read** (usually the full URL that was tried) and the reason (`timed out`, `HTTP 404`, `в ответе нет поля obj.brightness (в ответе: code, obj)`, `в файле 02_Зал.txt нет адресов контроллеров`, `не читается база PDQ: ...`). The header of the main page shows the count (`проблем: 3`) and turns red. The window is built for a human reading it: row order is **stable** (a repeat bumps the counter, it does not reorder — otherwise the table would reshuffle every second), **clicking a row copies a ready-to-paste line** (`[12:03:11] aoto: http://10.0.0.1:8080/x -> timed out (повторов 3, последний раз 12:03:40)` — `navigator.clipboard` where it exists, else the legacy textarea+`execCommand` fallback, called synchronously inside the click because a browser only allows that on a user gesture), and **Пауза** freezes the table (new problems still update the counter) so it can be read and copied calmly.

**Where the reasons come from.** `diag.record(source, target, message)` is called by the reader that failed, and `diag.resolved(source, target)` by the same reader once that target works again — so the log lists what is broken **now**, and a fixed device's row disappears by itself. Repeats fold into one row (`×180`), the ring keeps at most `DIAG_MAX` problems, and the target is deliberately the precise thing tried (a URL, `группа X`, `Зал/Ямкость`, `192.168.200.161:8088 node/detail`) so a wrong address in a group file is visible at a glance. Sources in use: `aoto` (`aoto._send` failures with the URL + reason, missing `commands.json`, an empty group file, a reply that lacks the field — the last one from `webstatus._note_missing_field`), `pixelhue` (each `_pull_*` names the call that failed), `pdq` (the database path / target list that cannot be read — why the ПК section is empty), `ping`, and `web` (a refresh that raised).

**What is shown** — four panels, all built from modules that already own the data:

- **AOTO** — per group, every parameter that can be *read*, **grouped by the device's own API section** rather than printed as one long list: `webstatus.section_of(path)` maps `/globalSettings/*` → «Картинка», `/input/*` → «Вход и тест-паттерн», `/system/*` → «Система» (unknown namespaces keep their own segment name), and each cluster is a grid of tiles (label above value). The parameter list is data, not code: the deck's status commands from `aoto/commands.json` first (including `hidden` ones such as `screen-status`, which is how the page shows the screen state), then the capture catalog `aoto/presets/parameters.json`. A catalog row reading exactly what a status command already reads is dropped, so `Яркость`/`HDR`/`Тест` are not listed twice (11 parameters per group with the shipped config — the capture catalog deliberately leaves out `scal`, which is the web UI's canvas zoom rather than a picture setting, see the Aoto guide). Values are aggregated by `aoto.status_text` — the same function the deck uses — so the two can never disagree (`700-1200`, `200 (1/2)`, `HLG` via a command's `labels`), and brightness additionally gets the nits-plus-%-of-ceiling figure (`47-80%`) from `aoto.brightness_limit`. Per-controller values ride along in the JSON and in each tile's tooltip. **The screen tile reads as words, not numbers, and as a combination**: `screen-status` (`obj.screenStatus`) has its own `labels` in commands.json (`0 картинка / 1 блэкаут / 2 фриз` — the device's own words: its UI writes `Blackouting` for 1 and `Freezeing` for 2 and nothing for 0), and `webstatus._screen_param` appends `+ тест цвет` per controller while the colour test pattern flag (`obj.testPicEn`, the deck's `Тест`) is on — that flag is independent of the overlay, so blackout/freeze and the test can be true at once, and the combination is built **before** aggregation (`блэкаут`, `картинка + тест цвет`, `фриз + тест цвет`; the `Тест` tile keeps its own `выкл`/`вкл`). Both fields are already read for the same group, so the combination costs no extra request, and dropping the `Тест` command from commands.json simply leaves the plain word.
- **PDQ** — the **deployment journal**: the newest `Deployments` rows with package, status (`идёт` / `ok` / `ошибка`) and target count, newest first, plus each row's targets, start/end and raw columns in the tooltip. Read by `pdq.recent_deployments` and cached separately: it **copies the whole database**, so it runs on `PDQ_STATUS_INTERVAL` (5 s) instead of the page's 2 s, and shows its own age. A missing DB/table/schema is a diag row (with the tables that DO exist), never a broken page.
- **PixelHue** — node online/offline + version + last error, Mapping, global **Затемнение**/**Стоп-кадр** (the deck's words for FTB/Freeze; on/off/частично across the usable screens), the screen list with its flags, and the preset count, from `pixelhue.node_state()`/`address()`/`screens()`/`mapping_enabled()`/`presets()`. Every badge and chip has a tooltip saying what it is (`FTB (Fade To Black) — плавное затемнение всего выхода`).
- **ПК** — the hosts of the active PDQ target list with their alias, ping state (`pcbrowser.status`) and the age of the last sweep (`pcbrowser.ping_age`). The sweep keeps its own cadence (`PING_INTERVAL`); the page never forces extra pings.

**Freshness and cost.** `GET /status` never does I/O: it returns the last snapshot plus its `age`, so a browser is never left waiting on a slow controller. A background thread (`webstatus.start()`) re-reads the devices every `WEB_REFRESH_INTERVAL` (2 s) but **only while a page is watching** — any `/status` request within `WEB_IDLE_TIMEOUT` (15 s) keeps it going, so a closed tab costs nothing and N open tabs share one refresh instead of multiplying the device load. A page landing on stale data wakes the thread early; a steady request stream does *not* speed the cadence up. One read at boot gives the first paint something to show. Within a refresh the PixelHue pull runs **concurrently** with the Aoto reads, because an unreachable device (4 requests × `PIXELHUE_TIMEOUT`) must not hold up the rest of the page.

**Reads are grouped by endpoint.** Parameters that come from the same reply cost **one** request per controller: `aoto.probe_raw` returns each controller's whole parsed reply and `aoto.field_value` pulls each field out of it, so a group's dozen `getGlobalSettings` parameters are read in one call instead of a dozen. (This is why the old `_status_text`/`_values_differ` are now the public `status_text`/`values_differ` — the page reuses them instead of duplicating the formatting.)

Knobs in [core/config.py](core/config.py): `WEB_PAGE`, `WEB_LOGS_PAGE`, `WEB_REFRESH_INTERVAL`, `WEB_IDLE_TIMEOUT`, `DIAG_MAX`.

## Conventions (keep these — they're why the code stays small)

These are the principles the codebase already follows. Match them when extending it:

1. **One module, one job.** Each `core/` file does exactly one thing (`osc` = wire format, `companion` = visual facade, `render` = diff+draw, `layout` = grid math, `loader` = tree from disk, `dispatcher` = press→action, `pdq` = PDQ, `pcbrowser` = the PC feature + shared catalog, `pdqmenu` = the batch-deploy menu, `aoto` = the LED-processor HTTP menu, `aotopresets` = the Aoto preset folder/file browser, `touch` = the TouchDesigner client-driven tab (its buttons come from the client over HTTP/OSC), `osc_buttons` = the generic OSC-message menu, `pixelhue` = the PixelHue Q8 HTTP-control menu, `ffs` = the FreeFileSync "Sync" tab, `develop` = the pull+restart / open-status-page tab, `progress` = the refresh progress bar, `webstatus` = the read-only web status page, `diag` = the "why did this read get no data" problem ring behind the log window). A new feature gets its own module rather than swelling an existing one (e.g. `pdqmenu` reuses `pcbrowser`'s catalog through its public API instead of duplicating it or bloating it).
2. **Only `render`/`companion` talk to Companion.** Every button update goes through `render.draw`/`render.update_cell` so the `PageState.rendered` diff cache stays truthful. Never call `osc`/`companion` directly from a feature — you'll desync the diff and push stale or duplicate updates.
3. **Config over constants-in-code.** Every tunable (ports, paths, timeouts, colors, intervals, grid size) has its **default** in [core/config.py](core/config.py) (per-machine values go in the ignored `config.local.json` — see "Machine-local configuration" above). Don't hardcode at the call site. Slot kinds and `ActionNode.after` values are named in [core/constants.py](core/constants.py) (`Kind`, `After`) — use those, never bare `"menu"`/`"back"` string literals.
4. **Fail soft at every external edge.** OSC, the PDQ CLI, the PDQ DB, ping, and user scripts must never crash the deck. Catch, log a warning, and surface the problem as button text (`ERR`) — the deck keeps working. The broad `except Exception` blocks are deliberate for this reason (marked `# noqa: BLE001`), and are only allowed at those I/O edges, not in core logic.
5. **Providers must be cheap.** A `provider`/`color_fn` runs on every render and press. Never do I/O (DB, network, subprocess) inside one — read from a module-level cache that a background thread or an explicit refresh populates (see `pcbrowser`'s catalog/ping caches).
6. **Hold the lock briefly; block outside it.** `state.lock` guards navigation state only. Long work (running a script, a PDQ deploy, OSC/DB I/O) happens *after* the `with state.lock` block so presses on other pages aren't stalled.
7. **Nodes are dataclasses; logic is small pure functions.** Prefer `from __future__ import annotations`, type hints, and functions that take data and return data (e.g. `pdq.deploy_args`, `layout.build_layout`) so behaviour is testable without a running deck.
8. **Verify the changed path before finishing.** No test suite yet (see below), so at minimum `python -c "import main"` and exercise the touched flow with `osc.send`/`pdq.run` monkeypatched — the pattern used throughout this project's development.

- **PDQ DB reads copy the whole file each call.** `pdq._connect` snapshots `Database.db`(+wal/shm) per call, so `refresh_catalog` does ~3 copies. Fine at start/reload frequency; batch into one snapshot if it ever gets hot.
- **Ping sweep redraws every page.** `render_all_pages` rebuilds layout for all pages every `PING_INTERVAL` even if none is on the PC subtree. Cheap (the diff pushes nothing when unchanged) but wasteful; could skip pages with no `color_fn` nodes.
- **Aoto status poller polls every group.** `aoto._poll_statuses` queries the status commands of *all* groups each `AOTO_POLL_INTERVAL`, not just the group currently on screen (it doesn't track which group is in view). Fine at a handful of groups/controllers; if it grows, scope the poll to the visible group (mirrors the ping-sweep gap above).
- **PixelHue poller polls even when the tab is not on screen.** `pixelhue._pull_all` fetches node detail + interface-location + screens + presets every `PIXELHUE_POLL_INTERVAL` regardless of which page is visible (4 small requests per cycle; fine for one device, but it could be scoped to skip when no page sits in the PixelHue subtree).
- **The status page reads every Aoto group while a tab is open.** `webstatus.refresh()` walks all groups and all parameters on each `WEB_REFRESH_INTERVAL` (one request per controller per **endpoint**, so ~3/controller with the shipped catalog) regardless of which section of the page is scrolled to, and an open-but-backgrounded tab keeps counting as a viewer until `WEB_IDLE_TIMEOUT`. Fine at a few groups; raise `WEB_REFRESH_INTERVAL` on a machine with many controllers, or scope the read to groups the page actually shows.
- **The log window keeps no history.** `core/diag.py` holds OPEN problems only: a device that recovers drops its row (and its repeat counter) with it, so "it was down for an hour this morning" is not recorded anywhere — the process log (`log.info("problem: ...")` on the first occurrence) is the only trace. Fine for "why is nothing displayed right now", which is what the window is for; add a bounded history ring if a real audit trail is ever needed.
- **A Touch client is only as fresh as its last POST.** The deck shows exactly the buttons of the last `POST /touch/buttons` — the server never pulls state from TouchDesigner, so a client that changes something without re-posting (or that only pings) leaves a stale label on the deck, and a press is fire-and-forget OSC with no acknowledgement (a client that missed it cannot tell). A dead client is removed within `TOUCH_CLIENT_TIMEOUT + TOUCH_SWEEP_INTERVAL`. All clients share the one Touch tab on every deck (they are not bound to a `DECK_PAGES` entry yet), which is fine while there is one TD project.
- **The PDQ journal reader is written against an UNDOCUMENTED schema.** PDQ publishes no API for its deployment history and the `Deployments`/`DeploymentComputers` column names above come from community tooling, not from PDQ; on this repo's machines it has only been exercised against a synthetic DB. It is deliberately forgiving (any column names, `rowid` ordering fallback, the whole row kept and shown in the journal tooltip, a schema error naming the tables that DO exist), but the field/label mapping may need one adjustment after seeing a real journal — `python -m core.pdq deployments` prints it. Reading it copies the whole DB every `PDQ_STATUS_INTERVAL`, which is the other reason that interval is 5 s and not the page's 2 s.
